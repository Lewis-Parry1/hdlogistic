The public-facing interface of \texttt{hdlogistic} adopts the Ports and Adapters pattern\cite{Hexagonalarchitecture},, subclassing \texttt{statsmodels.base.model.Model} and \texttt{statsmodels.base.model.Results}. This provides familiarity for users accustomed to \texttt{statsmodels} whilst keeping our core logic independent from the presentation layer.

The API is separated into two main classes following \texttt{statsmodels} convention, \texttt{MDYPLLogistic}, which handles model configuration and estimation, and \texttt{MDYPLLogisticResult} which deals with point estimates, model diagnostics and the high-dimensional corrections.

\section{Numerical Implementation}
\subsection{Caching}
Caching is an important concept used to avoid repeated computation when a result is requested after having already been evaluated. Within Python, one way it can be performed is with the \texttt{functools.cache} decorator, which hashes the arguments passed to the function, using them as a key for the stored result. If the function is called again with the same arguments, the underlying logic does not need to be re-executed, and the stored result can just be retrieved.

Caching is used in several places within our code, for example, the function \texttt{get\_hermite\_roots\_weights} users \texttt{functools.cache} to memoise the roots and weights required for two-dimensional Gaus--ermite quadrature.  Applying this ensures that this $\mathcal{O}(n^2)$ polynomial root-finding only runs once, meaning that subsequent calls can retrieve it in $\mathcal{O}(1)$ time.

\subsection{Vectorisation}
Vectorisation allows for mathematical operations on whole arrays to be run simultaneously rather than iterating scalar by scalar in higher level code.  In Python libraries such as \texttt{NumPy}, high-level function calls bypass the \texttt{CPython} interpreter loop and offload execution to a compiled C kernel that iterates over the underlying \texttt{ndarray} memory buffers, avoiding interpreter overhead and allowing for superior spatial cache locality and hardware-level vectorisation~\cite{harrisArrayProgrammingNumPy2020}.

Within our implementation, we use vectorisation in various places to improve performance. For example, during estimation and summary generation, linear predictors are computed with the matrix multiplication operator, which dispatches the evaluation to compiled \texttt{BLAS} routines that stream the design matrix across hardware vector registers. In addition to basic linear algebra, vectorisation is also applied directly to non-linear areas such as in computing the proximal operator, evaluating the Newton-Raphson root updates simultaneously. A final example is the evaluation of the state evolution equations, where vectorised cubature is implemented by applying Gauss--Hermite quadrature across both dimensions simultaneously. Rather than evaluating double integrals using nested Python loops, the quadrature nodes and weights are precomputed into 2D grids, allowing the integrand evaluation and weighted summation to execute entirely through compiled array operations.

\subsection{Stateless Design and Lazy Evaluation}
When writing mathematical and statistical code, it can be helpful to follow certain tenets of the functional programming paradigm. One example of this is the practice of separating data and computation, structuring pipelines as a series of stateless transformations and ensuring that the initial data record passed into the pipeline remains unaltered, helping eliminate side effects and preventing any leakage of state across model evaluations. Another useful concept from functional programming is writing deterministic functions, which depend only on their explicit arguments and neither read nor alter any global state. This is especially useful when implementing mathematical computations, as it ensures they match their theoretical formulations as closely as possible. Finally, lazy evaluation can also be useful, ensuring that expensive quantities are only computed when needed, avoiding unnecessary computational overhead.

Within our package, various examples of this can be seen. For instance, functions such as \texttt{compute\_deviance()}, \texttt{compute\_taus()} and \texttt{compute\_sloe()} are stand-alone functions operating purely on the arguments passed to them, ensuring they mirror their theoretical counterparts in the literature and making testing straightforward. In addition, we wrap the computation of certain computationally expensive quantities, such as leverages and the covariance matrix, within the \texttt{@cached\_property} decorator, deferring the cost until an explicit query occurs and caching the result for subsequent accesses. This ensures that if a user simply wants to use the model for estimation or scoring, they do not have to compute them unnecessarily.

\subsection{Package \& Dependency Management}

Following modern Python packaging standards and to guarantee reproducible installation and execution across platforms, we used \texttt{pyproject.toml}, a configuration file used by packaging tools to avoid having several disparate configuration files scattered across the repository. Complementing this is \texttt{uv}, a unified package and environment manager, which combines dependency resolution, lockfile synchronisation, and virtual environment management into one tool \cite{Uv}.

This allowed us to specify our target Python runtimes, various project metadata, and core numerical dependencies centrally, as well as segregate auxiliary tools into isolated dependency groups. Combined with the pinned lockfile from \texttt{uv}, anyone can easily reproduce the execution environment.


\subsection{Code Formatting \& Linting}
In software development, keeping a uniform code style and detecting syntactic issues manually can introduce significant friction in both the development and review process, diverting attention from issues with core functionality towards stylistic debates. In addition to this, chaining together multiple tools, such as Flake8 for style enforcement and Black for formatting, introduces substantial configuration complexity and runtime overhead. To resolve these issues, we used \texttt{ruff}, which unifies static rule enforcement and code formatting into one tool \cite{Ruff}.

All linting and formatting behaviours were configured under the \texttt{tool.ruff} table in \texttt{pyproject.toml}. We selected rule prefixes from \texttt{pycodestyle} (\texttt{E}) \cite{Pycodestyle2025} for PEP 8 compliance, \texttt{Pyflakes} (\texttt{F}) \cite{Pyflakes2025} for detecting unused imports and undefined variables, \texttt{isort} (\texttt{I}) \cite{Isort2026} for automated import sorting, \texttt{pep8-naming} (\texttt{N}) \cite{Pep8naming2025} for consistent naming conventions, and \texttt{pyupgrade} (\texttt{UP}) to enforce modern Python syntax.

\subsection{Static Type Checking}
Python is a dynamically typed language \cite{castagnaGradualTypingNew2019}, meaning that developers are not required to declare types for variables and function signatures, and the interpreter does not check types before the code is run. This provides flexibility when writing Python code and can make the process simpler; however, especially in bigger codebases, this can also reduce code readability and introduce bugs which are difficult to trace.

To rectify this, we made use of \texttt{mypy}, an open-source static type checker for Python \cite{vanRossum2020mypy}. By combining Python's native type hinting system with \texttt{mypy}'s compile-time type-checking, we were able to catch various bugs without having to run the code, improving ease of development.

Like the linter, \texttt{mypy} was configured within the \texttt{pyproject.toml} file within the \texttt{tool.mypy} section. We enabled strict type analysis which turns on \texttt{mypy}'s most comprehensive checks, forcing complete type annotations across all functions and disallowing untyped calls. To handle external dependencies that lacked proper typing, we installed \texttt{scipy-stubs} and selective type-checking ignore statements to prevent false-positives.


\subsection{Testing}
Although static type-checking, code linters, and code formatters do go a considerable way towards improving code quality and preventing syntactic or structural bugs, they cannot check semantic correctness or ensure that accurate numerical results are produced. A function can pass every linter check and satisfy our static type checking requirements but still give incorrect results.

To prevent this, automated tests that ensure single units of code are correct (unit tests), tests that ensure the code works correctly together (integration tests), and tests that ensure that the behaviour does not change when code is changed (regression tests) can be employed via unit testing libraries \cite{wilsonBestPracticesScientific2014}.

The primary way in which we achieve this is by utilising \texttt{pytest}, a testing framework designed for modular and scalable test suites. \texttt{pytest} provides automatic discovery of test modules and functions, along with modular fixtures to write reusable test setups \cite{Krekel2004pytest}.

We used this fixture system to construct reproducible synthetic datasets with various sample sizes and dimensions, and used parametrised tests to evaluate functions such as the state equation solvers across a variety of inputs. In addition to this, we used a variety of custom markers defined in \texttt{pyproject.toml} under \texttt{tool.pytest.ini\_options}. Specifically, the \texttt{brglm2} marker was used for tests validating against the reference R implementation, and the \texttt{candes\_sur} marker was used to benchmark solver convergence against values from \cite{zhao_sur\_candes\_2022}.

\subsection{Continuous Integration}
Although linters help developers maintain code quality, running them manually can be disruptive, and it is easy to forget to execute the checks before pushing changes. To ensure that non-compliant code does not enter the codebase, Continuous Integration tools can be used to automatically run these checks upon pushing code.

To implement this, we used \texttt{GitHub Actions}, along with \texttt{pre-commit} \cite{Precommit}. Defined in \texttt{.github/workflows/pre-commit.yml}, our pipeline triggers automatically with every \texttt{push} and \texttt{pull request}, performing trailing whitespace stripping, enforcing final newlines, and validating configuration syntax, as well as running \texttt{ruff}, \texttt{mypy}, and \texttt{pytest}.

\subsection{Code Documentation}
Comprehensive documentation serves a variety of essential purposes for both end users and developers. Internally, in-code documentation provides the necessary context to understand the codebase, maintain existing functionality and implement new features. Externally, users rely on public-facing documentation to interact with the package without having to understand the underlying implementation. Maintaining both external and in-code documentation independently however can introduce additional overhead and cause the external documentation to become out of date. Automating the extraction of external documentation from source code can eliminate this overhead and ensure that it remains in sync with the actual implementation~\cite{forwardRelevanceSoftwareDocumentation2002}.

In order to do this, we used \texttt{numpydoc} style docstrings within the source code~\cite{StyleGuideNumpydoc}, and used \texttt{Sphinx}~\cite{SphinxSphinxDocumentation} to automatically generate the external documentation. Configured under \texttt{docs/source/conf.py}, we rely on extensions such as \texttt{sphinx.ext.autodoc} to automatically document classes and functions, and \texttt{sphinx.ext.napoleon} to parse the NumPy docstring syntax into reStructuredText.

\subsection{Collaborative Development \& Version Control}


When developing software in a collaborative setting, using a version control system is essential for coordinating different contributions. The standard tool for this is Git, which allows every change to the codebase to be tracked. This provides a full history of the project, allowing developers to easily roll back mistakes and view past versions. Complementing this are remote repository hosting services such as GitHub.

To implement this, we used a local Git repository synchronised with a remote repository hosted on GitHub, configuring branch protection rules to disallow direct pushing to the main branch and doing all modifications through pull requests, developing new features on isolated branches and performing peer reviews. During the review process we used GitHub's built-in code review interface along with the Conventional Comments specification\cite{slaughterConventionalComments} which formats review comments with standardised labels and ensures that feedback is clear and actionable.
